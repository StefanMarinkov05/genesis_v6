# От спецификация към данни за зареждане

Генерирано приложение, което се отваря на празни таблици, не е демо, а база. Seed-ът съществува, за да изглежда първото пускане като използван продукт: редове във всеки списък, снимки на всяка карта, история на поръчки, коментари и гласове, потребители, които притежават нещо.

## Договорът на един екран

```json
{
  "Brand":    [ { "refKey": "brand-1", "Name": "Samsung" } ],
  "Product":  [ {
      "refKey": "prod-1",
      "parentRef_Brand": "brand-1",
      "parentRef_Category": "cat-1",
      "Title": "Смартфон Samsung Galaxy A54 128GB",
      "Price": 520.0,
      "Quantity": 1,
      "UserId": "$seedUser:1",
      "imageKeywords": ["samsung galaxy smartphone front view",
                        "samsung galaxy smartphone side view"]
  } ],
  "OrderItem": [ { "parentRef_Order": "order-1", "parentRef_Product": "prod-1",
                   "Quantity": 1, "UnitPrice": 520.0 } ]
}
```

| Поле | Задължително, когато | Правило |
|---|---|---|
| ключ на модел | моделът има `seeding.rowsPerModel` | по един масив, **поне** толкова реда |
| `refKey` | моделът е родител | уникален, kebab-case, латиница |
| `parentRef_<Target>` | има `manyToOne` връзка | трябва да сочи `refKey` от същия файл |
| декларирано свойство | освен ключ, външен ключ или nullable | типа на свойството; дати ISO-8601, пари като число |
| поле `…UserId` | спецификацията го декларира | `"$seedUser:0"`, `:1`, … по реда на `seedUsers` |
| `imageKeywords` | моделът има блок `images` | масив: точно **1** за `single`, **2–4** за `multiple` |

Обектите са затворени: излишно поле е грешка. Никакъв ID не се пише — базата дава ключовете, а `SeedData.cs` пази съответствието `refKey` → реален ключ.

## Защо символни връзки, а не ID-та

Моделът не може да знае какво ще даде SQL Server, а човек не може да държи номерата в синхрон при повторно пускане. Затова редовете се сочат по име. `Data/SeedData.cs` вмъква моделите в **топологичен ред** (родителите първи), пази реалните ключове и после свързва децата. Затова един модел може да е едновременно дете (Product → Brand) и родител (Product ← OrderItem).

## Къде живее файлът

| Път | Роля |
|---|---|
| `prompts/in/seed-response.json` | каноничният обмен — това чете етапът `seed` |
| `seeds/*.json` | доставени кандидати; изборът се копира на горния път |
| `prompts/out/seeds/<project>-seed.json` | архив на използваното при успешно генериране |
| `<out>/<Project>/Data/seed-data.json` | същите данни **вътре** в приложението (четат се при старт) |

## Писане на ръка

Хранилището съдържа преносим skill (`utils/claude-skills/dps-nn-seed-authoring`), който възпроизвежда собствения prompt на етапа, за да може чат клиент да произведе файла без пускане. Две негови поведения: пита за броя seed потребители, преди да пише; и остава кратък — генерирането на данни е механично, щом спецификацията е готова.

Правилата за съдържание:

1. Български за всяка четима стойност при `meta.language = bg`; марките в оригинал.
2. Реални градове, правдоподобни цени и дати — без „Test 1“ и lorem ipsum.
3. Няма два реда с един и същ описателен низ.
4. Спазвайте `seedHint`, ако е даден.
5. Дати ISO-8601; десетичните са числа.
6. Разпределяйте собствеността между потребителите.
7. **Сценарийно покритие**: каталози с артикули, непразна количка, минали поръчки, взаимно следване, отзиви, насочени към различни потребители, разпръснати коментари и гласове.

Правило 7 отделя демото от изсипана таблица и е най-често пропусканото.

## Снимки

Всеки ред на модел със снимки носи `imageKeywords`. Етапът изтегля по един файл на фраза, именува го `{model}-{row}-{img}.jpg` и кешира в `.image-cache/`, за да не струва повторното генериране заявки. Доставчици: Pexels, Pixabay, Picsum без ключ, или локална папка с `--image-pack`. Приложението сервира файловете от `wwwroot/images/…` и никога не сочи външен URL. Доставените резервни варианти покриват неуспешно изтегляне.

## Валидация, повторно използване и типичните провали

Етапът строи JSON Schema от текущата спецификация. Две следствия: валиден `Data/seed-data.json` се **преизползва** и обменът се пропуска; промяна в моделите прави стария seed невалиден и той се генерира наново.

Съобщенията на валидатора са на самата библиотека за JSON Schema, с представка пътя до реда, който е паднал; таблицата назовава провала, вместо да го цитира.

| Провал (какво казва съобщението) | Причина | Поправка |
|---|---|---|
| липсва задължителното свойство `parentRef_Brand` | моделът е дете, но редът няма връзка към родител | добавете връзка към `refKey` от същия файл |
| липсва задължителното свойство `refKey` | моделът е родител (друг модел сочи към него) | дайте уникален `refKey` на всеки ред |
| `Value is "string" but should be "array"` при `imageKeywords`, или грешен брой елементи | единичен низ, или 3 фрази за `single` | 1 фраза за `single`, 2–4 за `multiple` |
| `All values fail against the false schema` | поле, което не е в модела (затворените обекти така отхвърлят непознати ключове) | премахнете го — бележки само за съдържанието принадлежат на `seedHint` или никъде |
| твърде малко редове | под `rowsPerModel` | добавете редове или намалете броя в спецификацията |
| `verify` хваща английски | английско описание в данните | българско съдържание (ключовите думи са единственото разрешено английско поле) |

## След като данните влязат

Генерираното приложение зарежда данните само при старт, пазено от проверка „вече заредено ли е“ върху първия модел, така че рестарт не дублира редове. За умишлено презареждане: изтрийте базата (или сменете името ѝ) и пуснете отново — `SeedStage` помни в `logs/<Project>/db.json` коя база е мигрирана.
