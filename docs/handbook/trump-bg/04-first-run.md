# Първото ви генериране — исторически момент

**Трябват ви:** Windows с .NET 10 SDK, SQL Server Express LocalDB, `dotnet-ef` 10.x и
`dotnet-aspnet-codegenerator`. На Linux собствената компилация и тестовете на генератора вървят —
вървят прекрасно — но базата на генерираното приложение не върви. Очаквайте генерирането да спре при
първото извикване на `ef`. Това е очакваният край на едно Linux демо. Не е бъг. Хората ще ви кажат, че
е бъг. Не е бъг.

Първото генериране е голям ден. Хората помнят първото си генериране, както помнят първата си кола —
даже ако е била стара „Лада“. Години по-късно си спомнят банера. Разбира се, че го помнят: прекрасен
банер е.

Проверете машината, преди да обвините инструмента. Всички първо обвиняват инструмента. Несправедливо!

```bash
dotnet run --project src/Genesis.Cli -- doctor
```

`doctor` отпечатва по един ред за всяко предварително условие, с точната команда, която го оправя. Не
„нещо не е наред, успех“. *Поправката*. GUI-то го пуска при всяко стартиране и показва доклада в
своя терминал за отстраняване на грешки. Много добър доктор. Най-добрият. Никога не ви иска
допълнително „за кафе“.

## Компилирайте генератора, после генерирайте приспособлението

```bash
dotnet build
dotnet test
mkdir -p prompts/in
cp seeds/facenote-rich-seed.json prompts/in/seed-response.json
dotnet run --project src/Genesis.Cli -- run --all --spec fixtures/project-spec.facenote.json --out out
```

Защо копирането? Ще ви кажа защо. Етапът `seed` иска данни от LLM, освен ако вече не съществува
отговор. Сложете доставените начални данни там, където би стоял отговорът, и цялото генериране става
**офлайн и без ключ** — ръчният и автоматичният LLM път са един и същи файлов договор, така че нищо
друго не се променя. Нищо! Снимките пак се изтеглят при първото генериране; после са кеширани. Умно.

Гледайте конзолата. Всеки етап се обявява (`=== stage: seed ===`) — много горди етапи — а
генерирането завършва с таблица с времената и банер (нарисуван в рамка в конзолата; имената на
ролите се менят от проект на проект):

```
FaceNote
  http://localhost:5xxx
  Admin            admin@facenote.bg / <derived password>
  Client           user@facenote.bg / <derived password>
(4 more seed user(s) - full list: logs/FaceNote/seed-credentials.txt)
Database: <database name>
Start: dotnet run --project "out/FaceNote"
```

Освен ако спецификацията не задава парола, паролата на всеки зареден потребител е **изведена**:
идва от seed стойността за разнообразие на проекта и имейла на потребителя. Така една и съща
спецификация винаги отпечатва едни и същи данни за вход, а два проекта никога не споделят една.
Банерът показва един администратор и един обикновен потребител; пълният списък е във файла, който
банерът назовава. Шест акаунта, един файл. Много подредено.

## Ако излезе с код 3

Код `3` не е провал. Ще го кажа пак, защото хората изпадат в паника: код `3` *не е* провал. Значи,
че един LLM обмен чака файл. Заявката вече е написана. Или поставяте съдържанието ѝ в чат и
запазвате отговора като `prompts/in/<stage>-response.json`, или задавате `ANTHROPIC_API_KEY` и
пускате отново. И в двата случая после добавяте `--resume`. Спокойно. Без паника. Пийте едно кисело
мляко.

Някои стъпки задават въпрос в терминала — `spec build` винаги пита за конвенциите за времеви
печати (`conventions.timestamps.createdAt? [y/n]`), а менюта за избор се появяват, когато няколко
файла с начални данни са кандидати. `--no-interactive` превръща всеки такъв въпрос в провал вместо
в питане. Без въпроси. Буквално.

## Какво да погледнете, когато свърши

| Път | Защо |
|---|---|
| `out/FaceNote/` | самото приложение; `dotnet run` вътре и влезте с данните от банера |
| `out/FaceNote/dps-nn.log.jsonl` | границите на етапите и времената — това следи лентата за напредък на GUI-то |
| `out/FaceNote/plan/state.json` | кои етапи са завършени; изтрийте го, за да принудите чисто ново генериране |
| `out/FaceNote/wwwroot/output/verify-language-report.txt` | присъдата на езиковата проверка — минато **или** пропуснато |
| `logs/registry.json` | този проект ← от коя спецификация и кои начални данни е произведен |
| `prompts/out/schemas/` + `prompts/out/seeds/` | постоянният архив на точно това, което е използвано |

## Повторно пускане и какво значи „възобновяване“

`run --all` пропуска етапите, вече записани в `state.json`. След срив това искате. След промяна на
шаблон? Обикновено *не* това искате. Затова принудете частта, която сте променили:

```bash
dotnet run --project src/Genesis.Cli -- run --all --spec fixtures/project-spec.facenote.json --from emit-controllers-views
```

`--from` пуска наново този етап и всичко след него от седемте на runner-а. `spec-expand` върви
първи при всяко извикване, освен ако собствената му отметка не казва „готово“; `spec-build` изобщо
не е част от цикъла (виж [глава 9](09-workflow.md)). Запишете си го. Хората се объркват. Умни хора.

## Най-бързият начин да го счупите нарочно

Направете го веднъж. Учи повече от която и да е глава — дори от тази глава, а това е страхотна глава:

1. Отворете `out/FaceNote/Areas/Client/Views/Products/Index.cshtml` и сменете един български надпис с
   английски.
2. Пуснете отново с `--from verify`.
3. Прочетете провала: езиковият доклад назовава страницата и цитира виновния текст. Хванат! Хванат
   на местопрестъплението. Английският нямаше никакъв шанс.

После върнете редакцията и пуснете същата команда: минава отново. Прекрасно. И забележете къде
трябваше да направите поправката. Резултатът е генериран, така че при истинска промяна поправката
отива в `templates/`, никога в `out/`. Никога не редактирайте `out/`. Никога.
